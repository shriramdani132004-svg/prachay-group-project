# Demo Guide — PSPL Expense Voucher Management System

A presenter script covering every major screen and workflow. Total time:
~12 minutes. Screenshots of each step are in [`screenshots/`](screenshots/).

## Before you start

```bash
# 1. Database (if not already running)
docker compose -f docker-compose.dev.yml up -d

# 2. Backend
cd server && npm run dev          # http://127.0.0.1:3000

# 3. Frontend (new terminal)
cd client && npm run dev          # http://127.0.0.1:5173
```

Sign in with the provisioned demo accounts (see
[README §23](../README.md#23-demo-accounts)). The role shown in the UI always
comes from the server — there is no client-side role switcher.

---

## Scene 1 — Employee: create and submit a voucher (~3 min)

1. Sign in as **`rajesh.kumar@pspl.test`** (EMPLOYEE). The dashboard shows
   KPI cards (draft / pending / approved / rejected) computed from the
   database.
2. Open **My Vouchers** — a searchable, filterable table of *this user's*
   vouchers only.
3. Click **New Voucher**. Fill the form:
   - Expense title, date, department, category
   - Amount (e.g. `2450.00`) — note the live currency formatting
4. In the **Employee Signature** card, **draw** a signature on the canvas
   (or click to upload an image) and press **Use drawing**.
5. **Save as Draft** — the voucher appears in My Vouchers as `DRAFT` and is
   fully editable.
6. Open the draft, review, then **Submit for Approval**. Status becomes
   **PENDING_APPROVAL**; the edit/delete actions disappear (server-enforced —
   try editing via API and it returns 409).

> Talking point: the unique voucher number (`VCH-2026-…`) is generated by a
> database sequence; the signature is stored in a private vault, not in
> PostgreSQL.

## Scene 2 — Director: approve and reject (~3 min)

1. Sign out; sign in as **`arun.patel@pspl.test`** (DIRECTOR).
2. Open **Approval Queue** — organization-wide pending vouchers with search,
   filters and pagination.
3. Open a pending voucher (ideally the one just submitted). The document is
   **read-only** for the Director.
4. **Reject path**: click **Reject**, type a reason (≥ 10 characters — try a
   shorter one to see client+server validation), confirm. Status →
   **REJECTED**; the reason is visible on the employee's detail page.
5. **Approve path**: open another pending voucher, **draw the Director
   signature** on the pad below the document (or upload), then click
   **Approve** → confirm. Status → **APPROVED**.
   - Talking point: the Approve button is disabled until a Director
     signature exists; the server independently enforces this (422).

## Scene 3 — Accounts: register, analytics, print (~3 min)

1. Sign out; sign in as **`meera.nair@pspl.test`** (ACCOUNTS).
2. Open **Voucher Register** — organization-wide, read-only. Demonstrate
   search + filters (status, department, category, amount range).
3. Open a voucher detail: both **employee and director signatures** stream
   from the private vault (authenticated, role-gated).
4. Open the **Dashboard / Analytics**: status distribution, expense trends
   (daily/weekly/monthly), category breakdown, recent activity — all
   aggregated in SQL.
5. Click **Print / Save as PDF** — the print stylesheet produces a clean
   A4 receipt (browser print dialog → Save as PDF).

> Talking point: Accounts has **zero** mutation endpoints — every write
> attempt returns 403. This is server-side, not hidden buttons.

## Scene 4 — Security & session behaviours (~2 min)

1. **Logout** — cookie cleared, session row revoked; the old tab redirects
   to login on the next navigation.
2. Open DevTools → Application/Storage: **no JWT, no identity** in
   `localStorage` / `sessionStorage` — only HttpOnly cookies.
3. Expire or delete the session cookie client-side and reload: the SPA
   rehydrates via `/auth/me` and redirects cleanly when the session is gone.
4. (Optional, API-level) `curl` a voucher you don't own → `404` (ownership
   hidden); approve as an employee → `403`.

## Closing summary

| Requirement | Demonstrated |
| :--- | :--- |
| Draft → submit → approve/reject lifecycle | Scenes 1–2 |
| Mandatory signatures (employee + director) | Scenes 1–2 |
| Mandatory rejection reason | Scene 2 |
| Role isolation & read-only Accounts | Scenes 1–3 + Scene 4 |
| Analytics on real data | Scene 3 |
| Print / PDF export | Scene 3 |
| Secure sessions, no token in JS storage | Scene 4 |

For a fresh demo, reset the environment with:

```bash
docker compose -f docker-compose.dev.yml down -v
docker compose -f docker-compose.dev.yml up -d
cd server && npm run prisma:migrate:deploy && npm run prisma:seed
```

then re-provision demo passwords if needed (`npm run auth:provision-demo`).
